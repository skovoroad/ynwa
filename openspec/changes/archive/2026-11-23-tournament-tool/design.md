# Design

## Context

The project already ships `ynwa-simulator` (`ynwa-simulator/src/runner.rs`), which plays a single headless match and writes a JSON Lines recording whose footer carries the final score under `team_stats["A"|"B"]["score"]`. It prints only the recording path, not the score. See proposal.md for motivation.

Constraints that shape this design:

- Development environment is **Python 3.10.12** (no `tomllib`), and the tool is intentionally lightweight: no Rust, no tests, stdlib only.
- `record_game.sh` and `replay.sh` live at the repo root and compute `REPO_ROOT` from `dirname "$0"`; they are referenced by the `player-client` and `integration-testing` specs.
- The simulator binary is `target/release/ynwa-simulator`, which may not exist because development builds are debug.

## Goals / Non-Goals

**Goals:**

- Run a reproducible round-robin tournament over an arbitrary list of `teams/` folders by driving the existing `ynwa-simulator` binary.
- Emit two human-readable, space-aligned reports: per-match `results.txt` and aggregate `standings.txt`.
- Make each match reproducible by recording its seed, even though seeds are random by default.
- Co-locate the tournament tool and the existing shell wrappers under `tools/`.

**Non-Goals:**

- No new simulator or changes to `ynwa-core`/`ynwa-football`/`ynwa-simulator`.
- No machine-readable (CSV/JSON) output — two space-aligned text files only.
- No parallelism; matches run sequentially (order is deterministic, so parallelism could be added later without changing results).
- No display-name parsing; team identity is the folder name.

## Decisions

### Orchestrator language: Python 3.10, stdlib only

A Python script (`tools/tournament.py`) owns the tournament; a thin Bash wrapper (`tools/run_tournament.sh`) holds the parameters and calls it.

- **Why Python over Bash**: reading the `.jsonl` footer and computing standings is much clearer with `json`, `pathlib`, and `subprocess` than with `jq`/`awk`. Bash stays a thin parameter holder.
- **Why stdlib only**: Python 3.10 has no `tomllib`, and adding a TOML dependency just to read `display_name` is unnecessary — the spec uses folder names. `argparse`, `json`, `pathlib`, `subprocess`, `tempfile`, and `random` are all stdlib.
- **Alternatives considered**: a Rust `ynwa-tournament` binary (rejected: user asked for no Rust and no tests); pure Bash + `jq` (rejected: fragile JSON parsing).

### Release build lives in the Bash wrapper

`run_tournament.sh` runs `cargo build --release --bin ynwa-simulator` before invoking `tournament.py`, and passes the built binary's path. This keeps the Python script free of build concerns and satisfies "build release first" without rebuilding per match.

### Score extraction: parse the footer line

For each match, `tournament.py` writes the recording to a known path (`--out <dir>/<id>.jsonl`), runs the simulator, then reads the **last non-empty line** (the footer) and extracts `footer["team_stats"]["A"]["values"]["score"]` and `footer["team_stats"]["B"]["values"]["score"]`, casting to `int`. A missing `score` key means `0`, because the stat is only materialized once a goal is scored. A missing `team_stats` map or team entry is a hard error so format drift surfaces immediately. Because the runner controls which team is `--team-a` (home) and `--team-b` (away), the mapping back to home/away is unambiguous. A non-zero simulator exit aborts the run.

### Schedule: double round-robin

One round = every ordered pair `(home, away)` plays once, generated by nested iteration over the team list. `R` rounds repeat it, so each unordered pair meets `2R` times (equal home/away). This matches the confirmed "double round-robin" definition.

### Seeding: random per match, always recorded

Default: a fresh random `u64` per match from the system RNG, printed into `results.txt`. A fixed `--seed` derives each match's seed deterministically from the base seed and the match's position in the schedule (a seeded PRNG), so a full tournament is reproducible regardless of run order. This is what makes "discard recordings by default" safe: any match can be re-run from its recorded seed.

### Output files and directory layout

```
~/.ynwa/tournaments/<run>/
├── results.txt       # one row per match: round  home  away  score_home  score_away  seed
├── standings.txt     # team  P  W  D  L  GF  GA  GD  Pts
└── matches/          # only when --keep-recordings
    └── 0001_team_a_vs_team_b.jsonl
```

`<run>` defaults to a timestamp and can be overridden with `--name`. Columns are padded to the widest value in each column (space-aligned). Standings are sorted by points desc, then goal difference desc, then goals for desc, then team id asc.

### Recording retention: temp dir by default

Without `--keep-recordings`, each recording is written into a `tempfile.TemporaryDirectory()` and deleted after its score is read. With `--keep-recordings`, recordings go to `<run>/matches/` with a zero-padded match index in the filename.

### Shell wrapper relocation

`record_game.sh` and `replay.sh` move to `tools/`. Their `REPO_ROOT` becomes `$(dirname "$0")/..` so they still resolve the repo root, and the two specs that name `./record_game.sh` / `./replay.sh` are updated to `./tools/...` in the same change.

## Risks / Trade-offs

- **[Random seed by default → non-reproducible tournament]** → Mitigated by recording every match's seed in `results.txt`, so individual matches and (via a fixed `--seed`) whole tournaments can be reproduced.
- **[Parsing the footer couples the tool to the recording format]** → The footer layout is already a stable contract in `recording-and-replay`; the tool reads only `team_stats.*.score` (absent means `0`) and treats a missing `team_stats` map or team entry as a hard error so format drift surfaces immediately.
- **[Sequential execution is slow for large N or many rounds]** → Accepted for now; the schedule and seed derivation are order-independent, so parallelism can be added later without changing outputs.
- **[Moving shell wrappers breaks root-relative invocations]** → The two spec references are updated in this change, and the wrappers recompute `REPO_ROOT` correctly.

## Migration Plan

1. Create `tools/` and move `record_game.sh`, `replay.sh` into it, fixing `REPO_ROOT`.
2. Add `tools/tournament.py` and `tools/run_tournament.sh`.
3. Update the `player-client` and `integration-testing` specs (via this change's deltas).
