# Будущие идеи и задумки

## Извлечение системы принятия решений в отдельную библиотеку

**Дата:** 2026-02-04

### Описание
Возможность выделения логики принятия решений в отдельный crate `ynwa-decisions`.

### Обоснование
Система принятия решений уже имеет чёткую границу:
- **Вход:** JSON-контекст игрового состояния (ContextBuilder)
- **Выход:** Decision (enum с действием игрока)
- **Инициализация:** GameConfig (для получения скриптов игроков)

### Архитектура
```
ynwa-decisions library:
1. Инициализируется GameConfig (запоминает скрипты игроков)
2. Определяет ContextBuilder
3. Реализует полную логику принятия решений
4. Core становится клиентом этой библиотеки
5. Граница: сerde_json::Value как lingua franca
```

### Ключевые инсайты
- Объект Game не нужен при выполнении решения, только при инициализации
- Данные уже сериализуются (ContextBuilder)
- Код уже использует JSON внутри (LuaDecision)

### Преимущества
- Независимая разработка и тестирование
- Возможность переиспользования в других проектах
- Изоляция безопасности (Lua sandbox отдельно от core)
- Расширяемость (Python/ML движки принятия решений)
- Версионирование API через JSON-контракт

### Решение по типам
**Не создавать ynwa-types.** Использовать JSON-контракт вместо shared types.

**Причины:**
- Decision имеет глубокие зависимости: Region → GridCell, Point3D с uom
- Извлечение shared types потянет за собой всю domain model
- JSON-контракт проще, естественнее (уже используется), избегает complexity зависимостей
- Позволяет независимое версионирование библиотек

### Статус
**Отложено.** Текущая архитектура работает хорошо. YAGNI - не извлекать пока не потребуется.
