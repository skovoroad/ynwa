# Задача

Необходимо реализовать сериализацию/десериализацию результатов обсчёта игры.

Цели (по приоритету):

1. Записать и воспроизвести игру в плеере — игровая цель и отладка.
2. Интеграционное тестирование: игра обсчитывается с записью журнала, проверяется ожидаемая
   последовательность событий.
3. (отложено) Сетевая трансляция: событийная рассылка состояния вместо покадровой. В этой
   итерации не реализуется, но принятые ниже решения не должны закрывать эту возможность.

# Итоги обсуждения — предложения

## 1. Модель воспроизведения

Предлагается **событийно-управляемая пересимуляция физики**:

- При записи в журнал пишутся только существенные события (решения, исходы случайных веток,
  футбольные события, смены стадий) с таймстампами. Покадровая запись не нужна.
- При воспроизведении движок **не перезапускает** Lua и системы принятия решений
  ([`DecisionSystem`](ynwa-core/src/systems/decision/decision_system.rs:124),
  [`BallPossessionSystem`](ynwa-core/src/systems/ball_possession.rs:97),
  [`ActionSystem`](ynwa-core/src/systems/action.rs:79)): события подаются из журнала по
  таймстампам, а заново прогоняется только физическая часть ([`PhysicsSystem`](ynwa-core/src/systems/physics.rs:28)):
  бег игроков, полёт мяча с трением, прилипание мяча к владельцу.

Следствия:

- Воспроизведение точно повторяет исходный прогон при малом объёме записи.
- Снапшоты (§5) — коррекция численного дрейфа и точки произвольного доступа, но **не обязательны
  для корректности** воспроизведения.
- Снапшоты не исправляют логическое расхождение версий — его закрывает версионирование (§6).

## 2. Состав записи

Запись состоит из:

- **Заголовок**: версии (§6) + полный [`GameConfig`](ynwa-core/src/game.rs:228) (поле, сетка, зоны,
  игроки, преамбулы и скрипты). Конфиг неизменяем во время матча, поэтому сериализуется один раз.
- **Журнал событий** (§3).
- **Последовательность `delta_time`** — нужна для физической интеграции при воспроизведении
  (альтернатива — фиксированный шаг на время записи, но запись `dt` надёжнее при переменном rate
  плеера).
- **Снапшоты** полного состояния (§5).

## 3. Журнал событий

Каждое событие имеет таймстамп — абсолютное время шага, передаваемое системам аргументом в
[`World::step`](ynwa-core/src/world.rs:23). Предлагаемый набор событий:

- Решения игроков (`Stop` / `Run` / `Kick`) — вместо повторного вызова Lua.
- Исходы случайных веток: смена владения мячом, результат удара (фактическая скорость мяча после
  разброса).
- Футбольные события ([`FootballEvent`](ynwa-football/src/events.rs:8): гол, аут, угловой/удар от
  ворот, конец матча) и смены стадий.
- Сбросы решений, выполняемые менеджером игры при переходах в `Setup`.

Журнал должен быть доступен всем системам, включая футбольный слой. Предлагается буфер внутри
[`Game`](ynwa-core/src/game.rs:254) (по аналогии с `rng_manager`) с методом записи; события
таймстампятся аргументом `timestamp`.

## 4. Случайность (RNG)

Предлагается писать в журнал **исходы** случайных веток, а не сырые значения генератора:
потребителей случайности в игре всего два — борьба за мяч
([`select_winner`](ynwa-core/src/systems/ball_possession.rs:43)) и разброс удара
([`ActionSystem::Kick`](ynwa-core/src/systems/action.rs:109)). Это делает воспроизведение
независимым от порядка розыгрышей и внутренностей RNG.

## 5. Снапшоты

Снапшоты нужны. Состав — полный [`GameState`](ynwa-core/src/game.rs:238) + курсор журнала (номер
тика); при записи сырых значений RNG — ещё состояние RNG. Частота: фиксированный интервал
(например, 1 с) + на переходах стадий/событиях. Назначение: перемотка/seek в плеере, загрузка
промежуточного состояния, коррекция дрейфа.

## 6. Версионирование

Конверт записи содержит:

- `format_version` — версия схемы журнала/снапшота (сериализация).
- `engine_version` — версия семантики симуляции (`ynwa-core` + `ynwa-football`), поддерживается
  вручную и поднимается при любом изменении поведения (правила, константы, формулы). Не код-хеш —
  он даёт ложные отказы при рефакторинге.
- Встроенный [`GameConfig`](ynwa-core/src/game.rs:228) — запись самодостаточна и не зависит от
  изменившихся файлов команд/преамбул.

При десериализации — отказ при несовпадении `engine_version` с явным сообщением; опционально режим
принудительного чтения для отладки.

## 7. Детерминизм

- Для v1: гарантировать детерминизм в рамках одной платформы (задокументировать). Единственный
  реальный источник разброса — трансцендентные функции (`sin`/`cos` в направлении удара и
  `Arc`-зонах); при появлении требования кросс-платформенности — перейти на `libm`.
- Упорядочить итерации по `HashMap` (зоны — [`Field.zones()`](ynwa-core/src/field/mod.rs:59),
  статистика) для стабильного вывода сериализации; для логики с «первым совпадением» использовать
  детерминированный порядок.

## 8. Начальное состояние

- Для тестов достаточно начальных позиций с точностью до региона/стандартного ключа и начальных
  заданий — это выразимо уже сейчас через конфигурацию.
- Для игровых/отладочных целей произвольное начальное состояние задаётся загрузкой снапшота: в
  текущем коде произвольные позиции невыразимы ([`Game::with_stage`](ynwa-core/src/game.rs:265)
  расставляет игроков жёстко).

## 9. Сетевая трансляция

Отложена. Принятые решения (самодостаточные записи, версионирование, событийный журнал) совместимы
с будущей событийной рассылкой, поэтому дверь остаётся открытой.
