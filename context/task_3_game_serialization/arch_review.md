# Ревью архитектурного решения — task_3_game_serialization

Дата: 2026-09-22
Ветка: `task_3_game_serialization`

Ревью проводилось по файлу [`task.md`](task.md) (раздел «Архитектурное решение (шаг 2)») и
актуальному коду ядра и футбольного слоя. На этой стадии код не писался.

## Резюме

Основная модель решения — **событийно-управляемая пересимуляция физики**: журнал существенных
событий в ядре, отделённая от кодека модель `Record`, запись RNG исходами, replay-мир с
сокращённым набором систем — внутренне согласована и соответствует коду.

Физическая часть воспроизведения (позиции и скорости игроков и мяча, владение, стадии, счёт,
restart-поля) проработана корректно: порядок систем replay-мира (`ReplaySetupBallPlacer` →
`ReplayDriver` → [`PhysicsSystem`](ynwa-core/src/systems/physics.rs:28)) и порядок применения
событий внутри тика совпадают с исходным конвейером. Замечания ниже касаются в первую очередь
**контракта эквивалентности состояния** и ряда локальных нестыковок.

Обнаружено **одно блокирующее замечание** (З-1), требующее доработки решения на шаге 2, и
несколько незначительных замечаний (М-1 … М-6).

## Значительные замечания

### З-1. Контракт «одинаковый конечный `GameState`» невыполним в текущем виде

DOD этапа 4 требует: «исходный прогон и replay дают **одинаковый конечный `GameState`**».
Однако replay-мир намеренно не содержит
[`PlayerReactionSystem`](ynwa-core/src/systems/player_reaction.rs:22),
[`DecisionSystem`](ynwa-core/src/systems/decision/decision_system.rs:124),
[`BallPossessionSystem`](ynwa-core/src/systems/ball_possession.rs:98),
[`ActionSystem`](ynwa-core/src/systems/action.rs:80) и
[`FootballGameManager`](ynwa-football/src/game_manager.rs:50).
Часть мутаций этих систем над полями [`GameState`](ynwa-core/src/game.rs:238) не попадает в
журнал и не воспроизводится `ReplayDriver`'ом:

| Поле состояния | Кто меняет в исходном прогоне | Воспроизводится в replay? |
|---|---|---|
| `needs_decision` | `PlayerReactionSystem` (таймер реакции, каждый тик), `BallPossessionSystem` (при смене владения), `DecisionSystem`, менеджер | Только точечно: `PossessionChange`/`DecisionsReset` ставят `true`, `DecisionAssigned` снимает. Периодические подъёмы по таймеру реакции не журналируются. |
| `is_ready` | [`check_player_readiness`](ynwa-football/src/game_manager.rs:81) ставит `true` в `Setup`; сброс в `false` — через `handle_event` | `DecisionsReset` сбрасывает в `false`, но **ничто не ставит `true`** — менеджер в replay отсутствует. |
| `last_decision_time` | `DecisionSystem` (при успешном решении и при ошибке) | `DecisionAssigned` ставит `timestamp` безусловно — а при авто-`Stop` по прибытии и при назначении в `Setup` исходный код это поле **не трогает**. |
| `decision_reason` | `DecisionSystem` | `DecisionAssigned` ставит `reason` безусловно — а при авто-`Stop` и в `Setup` исходный код оставляет прежнее значение (в т.ч. «устаревшее» после события). |
| `last_error` | `DecisionSystem` (ветка ошибки), [`assign_setup_decisions`](ynwa-football/src/game_manager.rs:95) («missing region…», «unknown setup reason…») | `DecisionAssigned` ставит `None`; путь ошибки и ошибки расстановки **вообще не журналируются**. |

Корень проблемы: событие `DecisionAssigned` описывает **единственную** семантику присвоения
решения, тогда как в коде таких путей четыре с разными эффектами:

1. авто-`Stop` по прибытии ([`decision_system.rs`](ynwa-core/src/systems/decision/decision_system.rs:141)) —
   только `current_decision = Stop` и `decision_processed = false` (в `Setup` ещё `needs_decision = false`);
   `reason`/`last_decision_time`/`last_error` не трогаются;
2. успешное решение скрипта (`Ok`-ветка) — полное присвоение, как в таблице эффектов `task.md`;
3. решение из обработчика ошибки (`Err`-ветка) — ставит `last_error = Some(…)`, `decision_reason = None`,
   а `decision` может быть `None` (тогда и записывать нечего);
4. назначение в `Setup` (`assign_setup_decisions`) — только `current_decision` и `decision_processed = false`.

Таблица эффектов `ReplayDriver` в [`task.md`](task.md) предполагает семантику (2) для всех случаев,
поэтому точное равенство `GameState` недостижимо.

**Два варианта устранения (нужно выбрать на шаге 2):**

- **Вариант A (рекомендуется).** Явно определить «семантическую эквивалентность» replay:
  сравнивать только физически значимое состояние — позиции и скорости игроков, позиция/скорость
  мяча, `possessed_by`, `last_possessing_team`, `last_possession_change_time`, `stage`,
  `team_stats`, `restart_position`/`restart_team`, `elapsed_time`. Координационные флаги
  (`needs_decision`, `is_ready`, `decision_reason`, `last_error`, `last_decision_time`,
  `decision_processed`) объявить **вне контракта replay** и явно задокументировать. Это согласуется
  с моделью «пересимуляция физики, а не воспроизведение полного состояния».
- **Вариант B.** Журналировать и недостающие переходы (таймер реакции, `is_ready`, ошибки
  расстановки) и/или расширить `DecisionAssigned` дискриминатором источника/эффекта. Это
  противоречит цели «малый объём записи» и «только существенные события» — не рекомендуется.

Независимо от варианта DOD этапа 4 нужно переформулировать: либо указать подмножество сравниваемых
полей, либо (при варианте B) описать недостающие события. Также для воспроизводимости самого
интеграционного теста исходный прогон должен запускаться с детерминированной RNG-конфигурацией
(`temperature = 0.0` или фиксированный `seed`) — сейчас это в решении не оговорено.

## Незначительные замечания

### М-1. `FootballGameManager` игнорирует аргумент `timestamp`

[`FootballGameManager::update`](ynwa-football/src/game_manager.rs:50) объявлен с `_timestamp`.
Для журналирования (`External`/`StageChange`/… с таймстампами) ему придётся использовать аргумент
`timestamp`. Дополнительно [`check_game_end`](ynwa-football/src/events.rs:110) сравнивает с
`game.state.elapsed_time`, которое внутри тика ещё «старое» (обновляется в конце
[`World::step`](ynwa-core/src/world.rs:23)); это существующее поведение и на replay не влияет, но
при записи событий нужно явно решить, каким временем таймстампится `GameEnd`.

### М-2. Терминология «Recorder» используется в двух смыслах

В этапе 2 «Recorder (в память) поверх `JournalSink`, собирающий `Record`», а в §4.1 `Recorder` —
потоковая реализация поверх `RecordWriter + Write`. Стоит переименовать in-memory сборщик
(например, `RecordBuilder`) во избежание путаницы.

### М-3. Ошибки ввода-вывода при потоковой записи

`JournalSink::push` возвращает `()`, поэтому `Recorder` поверх `Write` не может пробросить ошибку
записи в момент события. Нужно явно описать контракт: ошибки буферизуются и возвращаются в
`finish()` (а `NullJournalSink` ошибок не даёт).

### М-4. Строковый эскейп `External { kind, data }`

`kind: String` + `serde_json::Value` — осознанный способ не тянуть `FootballEvent` в ядро, но
`decode_football_events` обязан корректно обрабатывать неизвестный `kind` и некорректный JSON
(не паниковать). Стоит зафиксировать это в описании функции.

### М-5. `StatUpdate` несёт только `delta`

Текущий код пишет статистику только через [`StatSet::increment`](ynwa-core/src/game.rs:23)
(`"score"`), поэтому `delta` достаточно. Но если в будущем понадобится абсолютный `set`, событие
его не выразит. Либо задокументировать ограничение, либо предусмотреть вариант `set`.

### М-6. Случайный пустой файл в папке задачи

В папке задачи закоммичен пустой (0 байт) файл
`context/task_3_game_serialization/ynwa-football/src/game_manager.rs:52` — вероятно, артефакт
(похоже на попытку сделать ссылку на строку). Его следует удалить; к решению задачи отношения не
имеет.

### М-7. Чтение «оборванного» файла

Тест «обрыва» файла в этапе 3 предполагает, что читается валидный префикс. Нужно определить
поведение `JsonRecordCodec::read` при неполной последней строке (игнорировать неполную строку, а не
падать), иначе заявленное свойство «при падении файл остаётся читаемым» не выполнится для хвоста.

## Вывод

Решение требует доработки на шаге 2 в части **контракта эквивалентности состояния** (З-1):
необходимо явно определить, какие поля `GameState` сравниваются при replay, и переформулировать
DOD этапа 4. После устранения З-1 остальные замечания (М-1 … М-7) могут быть учтены при
кодировании (шаг 4) и не блокируют переход.
