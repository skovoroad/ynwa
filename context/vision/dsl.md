# О чём тут

Документ представляет собой приблизительный набросок ожиданий от будущего DSL. Он не является спецификацией, не прошёл никаких проверок, и может быть изменён в любой степени.

Результатом его обсуждения должны стать окончательное описание, а также формальная спецификация, формальная грамматика ebnf и вообще все необходимые для разработки артефакты

# Установки при проектировании DSL 

При проектировании игры и DSL надо учитывать следующие вещи:

1. Пользователь игры - не профессиональный программист. DSL должен быть простым. Ожидается, что он содержит оператор ветвления (if/then/else), переменные, булевые и арифметические операции и вызовы функции стандартной библиотеки для двух целей: получить данные о состоянии поля и вернуть данные о принятом решении.
2. Пользователь не может добавлять настоящие собственные функции (их добавляет только разработчик игры), но он сможет добавлять "именованные блоки" позволяющие избегать дублирования пользовательского кода. Они описаны ниже.
3. Анализ игровой ситуации должен быть ограничен возможностями стандартной библиотеки. Пользователь не может программировать сложную логику игрока вроде "перебери всех игроков, для каждого рассчитай расстояние до меня, найди минимум", вместо этого должен быть вызов функции стандартной библиотеки типа "посчитать игроков в радиусе" или "вычислить расстояние между позициями"
4. DSL должен обладать строгой системой типов, но она скрыта от игрока, не требует синтаксиса для задания типов. Типы выводятся и проверяются на этапе трансляции в Луа. Основные типы (список открытый): число (для расстояний), булевое (для условий), игрок,  регион, зона, позиция.
5. Чтобы сократить количество ветвлений, пользователь пишет задания игрока для предопределённых ситуаций: "мяч у меня", "мяч у моей команды", "мяч ничей", "мяч у чужой команды". Каждому игроку, таким образом, даётся комплект заданий, а не одно.
6. Необходимо сформировать публичную терминологию. Например, вместо "именованные блоки" - "подпрограмма", вместо "тактическое задание" - какой-то простой запоминающийся термин, и так далее.
7. В разработке DSL мы должны отделять ядро языка: синтаксический анализ, семантический анализ и проч. от конкретной версии DSL для футбола (в идеале вся футбольная специфика должна быть скрыта в функциях стандарной библиотеки)
8. По возможности язык должен оперировать абстракциями предметной области: например, цикл не по номерам игроков (числа), а по игрокам.

# Перспективы

Ожидания от дизайна DSL: простота, возможно, близость к естественному (английскому) языку (это требует обсуждания). Полный контроль над развитием языка: пользователь не сможет определять функции, операторы, произвольно компоновать код. Он только пишет задание для конкретных игроков в конкретных ситуациях. Для повторного переиспользования пользовательского кода будет предложена концепция "именованных блоков кода", которые могут использоваться как в тактическом задании игрока, так и в общекомандном коде.

В будущем пользователь будет строить задания не только при помощи написания кода, но и с помощью конструктора кода (который не позволяет писать некорректный код, что-то вроде продвинутого автокомплита), а следующий шаг - с помощью ИИ. Но это будущие этапы.

Возможно, в будущем будут реализованы другие виды спорта. На уровне кода такое разделение есть уже сейчас. Поэтому в DSL тоже должно быть предусмотрено разделение уровней ответственности (незаметное для пользователя): ядро языка и спортивная составляющая.

Интерпретатор DSL не нужен: код будет транспилироваться в Lua. Уже сейчас поддержка кода на Lua есть в проекте. При разработке DSL должна учитываться необходимость такого транспилирования, нельзя задумывать конструкции, которые невозможно будет выразить в Lua или невозможно выразить в протоколе обращения из Lua к ядру игры.

На текущий момент нет цели использовать несколько тактик в игре, делать замены, и вообще управлять игрой: пользователь вносит изменения только между играми. Но в будущем такая возможность может появиться, и принятые решения не должны противоречить такой перспективе.

# Примеры 

Примеры и конкретные решения по дизайну DSL предмет будущего проектирования. На текущий момент они не принимаются в рассмотрение как точный повод для принятия проектных решений, но могут учитываться в обсуждении.

Пример 1, использование ветвления:

    forward = player 10 of my_team      # variable; function: player ARG of ARG; predefined constant my_team
    if distance to forward < 10         # distance to - function (player) -> int
    [
        decision: pass to forward       # after 'decision' instruction code returns
    ]
    else
    [
        decision: run to region A1:B3   # region A1:B3 returns object of type 'region'
    ]
    # unreachable

Пример 2, использование именованных блоков:

    # Common team code:
    common_behavior = [                      # named block
        if me in opposite_goal_area          # operator 'in'
        [
            decision: kick to opposite_goal  # opposite_goal, opposite_goal_area are predefined variables
        ]
    ]

    # Player code:
    defender_1 = player 4 of opposite_team
    defender_2 = player 5 of opposite_team
    critical_distance = 5
    if distance_to defender_1 < critical_distance 
        or distance_to defender_2 < critical_distance
    [
        common_behavior
    ]

# Язык

## Свойства

- регистронезависимость
- свободное форматирование, нет разделителя между выражениеми, разрешены многострочные выражения
- строгая типизация, но типы выводятся, а не указываются в коде
- нет контейнеров
- ограниченный цикл по явному списку игроков (подробнее см. [dsl_cycles.md](dsl_cycles.md))

## Типы

- игрок
- регион
- позиция (игрока, мяча)
- зона (штрафная, половина поля, ворота)
- число (для расстояний)
- булевое значени. Нужны ли литералы True и False?
- функции (определены в стандартной библиотеки)
- decision: фунция, завершающая скрипт
- именованные блоки

## Синтаксис

блок кода: []
ветвление: if/then/else
цикл: см. [dsl_cycles.md](dsl_cycles.md)

    for player in teammates 6, 7, 8
        order by distance to me ascending
    [
        if player free
        [
            decision: pass to player
        ]
    ]
переменные: my_specific_distance = 1
функции: требуется принятие решение о синтаксисе
операторы: 
- булевы
- арифметические 
- pos in region A1:B2 # check variable pos, return boolean

## Именованные блоки

Мы не разрешаем пользователю создавать свои функции, но у пользователя должна быть возможность переиспользовать код. Предлагается ввести "именованные блоки", де-факто лямбды с полным захватом окружения.

Требуется решить все вопросы, связанные с захватом переменных, видимостью переменных и все возможные связанные с концепцией противоречия.

    defender_behavior = [
         # code
    ]

    use defender_behavior  # code block usage

# Открытые вопросы:
## Синтаксис функций
В примере использованы функции, состоящие из нескольких токенов:

    player 10 of my_team
    pass to forward

С одной стороны, если заменить "pass to forward" на "pass_to forward", мы сможем явно отличать имя функции от аргумента, когнитивная нагрузка на пользователя упадёт
С другой стороны, используя имена функций в один токен, мы не сможем использовать выразительные конструкции вроде "player 10 of my_team", близкие к натуральному языку.
