# Порядок работы над задачей в проекте

## Общие сведения
Работа над проектом ведётся человеком и ИИ-ассистентом. В каждом шаге указано

- кто за что отвечает
- порядок действий
- DOR - что надо проверить до выполнения шага
- DOD - какой эффект должен быть в конце каждого шага

Результатом выполнения каждого шага должен быть как минимум один коммит (исключение: шаг 3 на этапе исправлений)
Если ИИ-ассистент обнаруживает противоречия в требованиях, он останавливает работу и указывает на эти противоречия.

Шаги должны выполняться каждый раз в новом только что начатом диалоге с ИИ-ассистентом.

Если на каком-либо шаге обнаруживается, что DOR не выполнен, задача невыполнима или требует изменения архитектуры всего проекта или полной переформулировки задачи, ИИ-ассистент указывает на это человеку. После чего по согласованию с человеком работа либо останавливается, либо продолжается.

В проекте нет CI/CD, изменения производятся локально и пушатся человеком вручную. 

ИИ работает в режиме агента и может выполнять команды git, cargo и проч. 

Соглашения:
- папки задачи = имя ветки
- в файле task.md после шага 1 есть как минимум один раздел: "Задача"

## Шаг 1: постановка задачи
Этот шаг выполняет человек. ИИ-ассистент не участвует.
В папке с названием task_<номер_задачи>_<говорящий_текстовый_идентификатор> создаётся файл под названием task.md
Создаётся ветка с тем же названием.
В файле task.md в свободной форме описывается задача
DOD - git переведён на ветку с задачей. в папке задачи лежит файл task.md, в нём описана задача. он закоммичен.

## Шаг 2: анализ требований и выработка архитектурного решения
Этот шаг выполняют ИИ-ассистент и человек. 
DOR: 
- выполнен DOD шага 1.
- git переключен на ветку задачи.
- начат НОВЫЙ диалог с ИИ-ассистентом

На этой стадии не пишется код, производится подготовка архитектурного решения для задачи.

Порядок работы:
- ИИ-ассистент читает файл context/context.md для ознакомления с проектом.
- ИИ-ассистент читает файл task.md из папки задачи.
- ИИ-ассистент читает дополнительную документацию, если это надо.
- Если на момент выполнения шага в файле task.md есть замечания после ревью постановки задачи, следует добиться исправления этих замечаний и подтверждения от человека, что их можно стереть.
- Если на момент выполнения шага в файле task.md нет замечаний после ревью, то происходит уточнение текстовой постановки задачи. ИИ-ассистент проводит анализ, уточняет непонятные вопросы по постановке задачи у человека. Если вопросов нет, то проверяет, что задача реализуема, что постановка непротиворечива. ИИ-ассистент ищет альтернативные решения: можно ли упростить задачу, использовать архитектурные шаблоны. Описав результаты анализа, ИИ-ассистент добивается от человека подтверждения: нужно ли отредактировать постановку задачи. При необходимости поисходит несколько итераций редактирования, пока человек не подтвердит постановку задачи. После этого файл task.md в окончательном виде коммитится.
- Если на предыдущей стадии не были согласованы конкретные типы и программные интерфейсы, то по той же процедуре происходит их согласование.
- Итоговый файл коммитится.

DOD: архитектурное решение описано в файле task.md в папке задачи, согласовано и закоммичено в ветку задачи.

## Шаг 3: ревью архитектурного решения
Этот шаг выполняют ИИ-ассистент и человек. 
DOR: 
- в папке с задачей есть файл task.md с постановкой задачи и архитектурным решением по ней.
- git переключен на ветку задачи.
- начат НОВЫЙ диалог с ИИ-ассистентом

На этой стадии не пишется код. Производится ревью архитектурного решения для задачи.
Порядок работы:
- ИИ-ассистент читает файл context/context.md для ознакомления с проектом.
- ИИ-ассистент читает файл task.md из папки задачи.
- ИИ-ассистент читает дополнительную документацию, если это надо.
- ИИ-ассистент проводит ревью описанного в файле task.md решения и выводит результаты своего анализа.
- Если замечания незначительные, они исправляются по согласованию с человеком. В файле task.md ставится отметка, что ревью пройдено.
- Если замечания значительные, они дописываются в файл task.md и коммитятся. После этого человек вернётся к шагу 2.

DOD: одно из двух: или в файле task.md ставится отметка, что ревью пройдено и архитектурное решение согласовано, либо в нём дописан список замечаний. Файл закоммичен.

## Шаг 4: кодирование 
Этот шаг выполняют ИИ-ассистент и человек. 
DOR: 
- в папке с задачей есть файл task.md с постановкой задачи и архитектурным решением по ней.
- в файле task.md есть отметка, что решение заапрувлено.
- git переключен на ветку задачи.
- начат НОВЫЙ диалог с ИИ-ассистентом

На этой стадии пишется код. 
- ИИ-ассистент читает файл context/context.md для ознакомления с проектом.
- ИИ-ассистент читает файл task.md из папки задачи.
- ИИ-ассистент читает дополнительную документацию, если это надо.
- Если код уже написан и проревьюирован (в папке задачи есть файл review.md), то ИИ-ассистент исправляет написанный код на основании замечаний из  review.md из папки задачи. Файл review.md удаляется (он всё равно есть в истории гита)
- Если код по задаче ещё не написан, ИИ-ассистент пишет код на основании архитектурного решения и требований к коду, описанных ниже.
- Человек проводит ревью, ИИ-ассистент исправляет.
- ИИ-ассистент добивается выполнения тестов.
- Итоговый вариант коммитится в ветку. 

Требования к коду смотри в разделе "Требования к коду"

DOD: код написан, согласован человеком, закоммичен.

## Шаг 5: ревью 
Этот шаг выполняют ИИ-ассистент. 
DOR: 
- в папке с задачей есть файл task.md с постановкой задачи и архитектурным решением по ней.
- в файле task.md есть отметка, что решение заапрувлено.
- git переключен на ветку задачи.
- закоммичен код, решающий задачу
- начат НОВЫЙ диалог с ИИ-ассистентом

На этом шаге ИИ-ассистент проводит ревью закоммиченного решения.
- ИИ-ассистент читает файл context/context.md для ознакомления с проектом.
- ИИ-ассистент читает файл task.md из папки задачи.
- ИИ-ассистент читает дополнительную документацию, если это надо.
- ИИ-ассистент проводит ревью закоммиченного решения. В числе прочего, при ревью следует руководствоваться требованиями к коду (раздел "Требования к коду"). Если есть замечания, ни пишутся в файл review.md, файл коммитится. 
- Если замечания несущественные, то они правятся сразу по согласованию с человеком. Если замечания существенные, то человек перейдёт к шагу 4. 

DOD: одно из двух: код исправлен, согласован человеком, закоммичен, либо создан файл review.md с замечаниями и закоммичен уже он.

## Шаг 6: Финализация, оформление документации и вливание в основную ветку
Этот шаг выполняют ИИ-ассистент и человек.
DOR:
- git переключен на ветку задачи.
- закоммичен код, решающий задачу
- файл review.md отсутствует в папке задачи.
- тесты/clippy/fmt зелёные

Что делать:
- ИИ-ассистент правит документацию (context/context.md) и другие документы, если это указано человеком. При этом недопустимо делать не относящиеся к задаче изменения.
- человек проводит ревью документации.
- если от человека получено разрешение, документация коммитится.
- производится мёрж ветки в ветку мастер.

DOD: 
- документация учитывает изменения, произошедшие при решении задачи 
- ветка смёржена в мастер.


## Требования к коду

- Код должен быть по возможности простым. Если есть возможность избежать шаблона, трейта в пользу простых структур и функций, это следует сделать.
- не нужны очевидные комментарии: комментарии только к неочевидным местам. Комментировать только неочевидное: «почему», а не «что». 
- говорящие идентификаторы
- проекту свойственна высокая комбинаторика, поэтому следует добиваться максимального покрытия тестами, по возможности параметризованными.  Юнит-тесты в отдельных файлах `*_tests.rs` рядом с реализацией, подключаются через
`#[cfg(test)] #[path = "..."] mod tests;` — это уменьшает размер файлов реализации и контекст для агентов. Тривиальные присваивания не тестируются; проверяются логика, границы, интеграция.
- разумеется, все тесты должны быть зелёными.
- cargo clippy и cargo fmt не выдают предупреждений.
- Типобезопасность (например, `uom` вместо `f32`), валидация в конструкторах через `assert!`,
- описание данными вместо алгоритмов, идиоматичный Rust (`Option`/`Result`), O(1) на горячих путях,
- YAGNI — реализуется только явно запрошенное в задаче или задании. Это важно! Ничего не выдумывать за пределами спецификации.
