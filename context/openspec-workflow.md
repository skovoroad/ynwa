# Памятка: работа по флоу OpenSpec (через Zed-агент)

Короткая шпаргалка, как вести задачи по процессу OpenSpec в этом проекте.

---

## Что такое OpenSpec в проекте

OpenSpec — инструмент spec-driven разработки. Задачи ведутся как **changes**, у каждого
change есть план (`proposal`, `design`, `tasks`) и дельта к требованиям (`specs`).

Ключевые папки:

| Папка | Что там |
|---|---|
| `openspec/changes/` | **Бэклог и текущая работа** — по одному change на задачу |
| `openspec/changes/archive/` | Завершённые изменения |
| `openspec/specs/` | **Текущие согласованные требования** (обновляются при `archive`/`sync`) |
| `openspec/config.yaml` | Проектный контекст и правила код-стайла |

Важно: будущие задачи копятся в `changes/`, а не в `specs/`. В `specs/` требования попадают
только после того, как изменение реализовано и заархивировано.

---

## Команды Zed-агента (слэш-команды)

| Команда | Назначение |
|---|---|
| `/opsx-explore` | Обсудить / продумать идею до того, как она станет задачей |
| `/opsx-propose` | Создать change со всеми артефактами (планирование, **без кода**) |
| `/opsx-apply` | Реализация кода по `tasks.md` |
| `/opsx-update` | Пересмотреть существующий change (план/артефакты) |
| `/opsx-sync` | Перенести delta-спеки change в основные `specs/` без архивации |
| `/opsx-archive` | Завершить и заархивировать change |

---

## Полный цикл задачи

1. **`/opsx-explore`** — обсуждение задачи, прояснение требований.
2. **`/opsx-propose`** — агент создаёт change: `proposal.md`, `specs/.../spec.md` (дельта),
   `design.md`, `tasks.md`. Код на этом этапе **не пишется**.
3. 🛑 **Human-in-the-loop**: человек читает `design.md` и `tasks.md`, вносит ручные правки,
   добавляет задачи. Затем — **git-коммит №1**.
4. **`/opsx-apply`** — агент пишет код по шагам из `tasks.md`.
5. 🛑 **Human-in-the-loop**: человек собирает проект и прогоняет тесты. Если есть ошибки —
   возвращает агенту лог. После успеха — **git-коммит №2**.
6. **Проверка** — агент проверяет сам себя, человек делает финальное ревью.
7. **`/opsx-archive`** — завершение и архивация change; его требования уходят в `specs/`.

---

## Два обязательных git-коммита

- **Коммит №1 «Спецификация утверждена»** — после `propose` и всех ручных правок
  в `design.md`/`tasks.md`, **до** того, как агент начнёт писать код.
- **Коммит №2 «Код написан»** — после успешной сборки, тестов и ревью, **до** вызова
  `/opsx-archive`.

Эти две точки фиксируют договорённости и результат, чтобы человек уверенно управлял циклом.

## Проверки кода (после `/opsx-apply`)

```sh
cargo build
cargo test
cargo clippy
cargo fmt -- --check
```

Ошибки возвращайте агенту в виде лога — он их исправит.

## Полезные CLI-команды (для проверки состояния)

```sh
openspec list                          # список changes
openspec show <change>                 # показать change
openspec status --change <change> --json   # статус артефактов change
openspec validate <change>             # валидация
openspec --version                     # должно быть 1.16.0
```

> CLI установлен как `@fission-ai/openspec` (v1.16.0). НЕ путать с npm-пакетом `openspec`
> (это чужой стаб-пакет, он не работает).

## Старые задачи (`context/tasks/`)

Задачи из старого флоу (`task_4`, `task_5`, `task_6`, `task_9`, `task_10`, `task_11`)
постепенно переносятся в `openspec/changes/` через `/opsx-propose`. Пока задача не перенесена,
её описание остаётся в `context/tasks/`; после переноса старую папку удаляют.
