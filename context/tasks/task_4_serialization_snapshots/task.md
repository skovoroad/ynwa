# Задача

Реализовать снапшоты полного состояния игры в записи и их использование при воспроизведении:
перемотка/seek, загрузка промежуточного состояния, коррекция численного дрейфа.

Выделено из задачи сериализации (`task_3_game_serialization`).

# Итоги обсуждения — предложения

## 1. Снапшоты

Снапшоты нужны. Состав — полный [`GameState`](ynwa-core/src/game.rs:238) + курсор журнала (номер
тика); при записи сырых значений RNG — ещё состояние RNG. Частота: фиксированный интервал
(например, 1 с) + на переходах стадий/событиях. Назначение: перемотка/seek в плеере, загрузка
промежуточного состояния, коррекция дрейфа.

Снапшоты — коррекция численного дрейфа и точки произвольного доступа, но **не обязательны для
корректности** воспроизведения (в минимальном решении `task_3_game_serialization` их нет).

## 2. Начальное состояние

Для игровых/отладочных целей произвольное начальное состояние задаётся загрузкой снапшота: в
текущем коде произвольные позиции невыразимы ([`Game::with_stage`](ynwa-core/src/game.rs:265)
расставляет игроков жёстко).

Этот же механизм обеспечивает визуальный контроль интеграционных сценариев task_8: сценарий
записывается как игра, снапшот начального состояния попадает в запись, а плеер применяет его перед
воспроизведением (record → replay).

## 3. Требуемые доработки (вынесены из task_3)

- `Snapshot` в модель записи (`record.rs`): `tick`, `timestamp`, `journal_cursor`, `state`.
- `Game::from_state(config, state, rng_manager)` — восстановление `Game` из снапшота.
- `PhysicsSystem::with_last_update(timestamp)` — восстановление `last_update` при seek.
- Захват снапшотов в `Recorder` (фиксированный интервал + на `StageChange`/`External`).
- `create_football_replay_world(record, seek_to)` — выбор снапшота и старт с его курсора.
- Применение снапшота как начального состояния при воспроизведении: запись начального снапшота в
  `Record` и старт воспроизведения с него (визуальный контроль сценариев task_8).

> Коллизия имени с task_8: task_8 добавляет в `ynwa-core` частичный тип `Snapshot` (поля-`Option`,
> частичное начальное/конечное состояние, метод `Game::apply_snapshot`). Здесь планируется отдельный
> тип `record::Snapshot { tick, timestamp, journal_cursor, state }` для записи. Два разных типа с
> именем `Snapshot` в одном крейте конфликтуют. Решение об окончательном имени (переименовать
> частичный тип task_8 либо назвать снапшот записи иначе) принимается на стадии работы над task_4.
