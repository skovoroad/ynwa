## Замечания

### 1. Отсутствуют автотесты для не-GUI логики (требует решения человека)

Раздел «Проверка» задачи: «Автоматические тесты для `ynwa-player` не добавляются (GUI)».
Но обоснование «(GUI)» не распространяется на новую чистую логику, не завязанную на графику:

- [`cli::parse`](../../../ynwa-player/src/cli.rs:17) — ручной разбор с ~10 ветками (все варианты
  ошибок, дефолты, игнорирование позиционных в replay), полностью тестируем;
- [`SimulationControl::for_replay`](../../../ynwa-player/src/simulation.rs:27),
  [`finished`](../../../ynwa-player/src/simulation.rs:80), `pace/should_step/consume_step` — чистая
  арифметика темпа;
- [`replay_steps`](../../../ynwa-player/src/main.rs:173) — чистая функция.

Это противоречит [`code_requirements.md`](../../code_requirements.md:8) (п. 4: «В новом коде
тестами покрываются все пути», параметрические тесты при высокой комбинаторике) и требованию шага 5
«Тесты должны проверять все ветки нового решения». Ни одного нового теста в коммите нет.

Противоречие между текстом задачи и проектными требованиями — по [`procedure.md`](../../procedure/procedure.md:12)
требует подтверждения человека: либо добавить юнит-тесты для `cli.rs`/`simulation.rs`/`replay_steps`,
либо явно зафиксировать исключение. Считаю замечание существенным (возврат к шагу 4), но решение
за человеком.

### 2. Сигнатура параметра `events` отличается от утверждённой архитектуры (несущественное)

В ревью архитектурного решения (шаг 3, п. 6) зафиксировано
`events: &[(f32, FootballEvent)]` и «в остальных режимах передаётся пустой срез».
В коде — [`Option<&[(f32, FootballEvent)]>`](../../../ynwa-player/src/main.rs:213) (`None` в
play/record). Наблюдаемый результат тот же (в play/record панель не рисуется), но сигнатура
отличается от утверждённой. Решение можно принять как более чистое (нет лишней отрисовки пустой
панели) — требуется явное согласие.

### 3. Тексты событий не совпадают с утверждёнными (несущественное)

Архитектура (шаг 3, п. 6) задаёт русские строки: «Гол: команда …», «Аут; последнее касание: …»,
«Лицевая; последнее касание: …», «Конец матча». В коде — английские:
[`"Goal: team A"`, `"Throw-in; last touch: A"`, `"Goal line; last touch: A"`, `"Match end"`](../../../ynwa-player/src/ui.rs:189).
Существующий UI англоязычный («Space - pause/resume», «Team A/B»), поэтому, вероятно, осознанно.
Семантика верна (в `Goal` забивает `conceding_team.opposite()`). Требуется подтверждение, что
отход от текста архитектуры допустим.

### 4. Отклонения от спецификации в сторону дополнительной функциональности (несущественное, YAGNI)

- [`replay_steps`](../../../ynwa-player/src/main.rs:173) добавляет фолбэк для записей без футера
  (шаги считаются по timestamp последнего события). Задача предписывает останавливаться после
  `record.total_steps`; фолбэк в спецификации не описан. Устойчивость полезна, но это незапрошенное
  поведение (см. [`code_requirements.md`](../../code_requirements.md:13), п. 9).
- Добавлены не упомянутые в задаче/архитектуре `record_game.sh`, `replay_game.sh` и переменная
  окружения `YNWA_GAMES_DIR` (используется только скриптом, плеером не читается).

### 5. Расхождение текста архитектуры с фактическим API (информационное)

В «Ревью архитектурного решения (шаг 3)» указано `env_home::home_dir()`, в коде используется
[`env_home::env_home_dir()`](../../../ynwa-player/src/cli.rs:104) — это корректное имя функции
актуальной версии `env_home` (код компилируется). Стоит поправить формулировку в `task.md`, чтобы
документ не расходился с кодом.

### 6. Граничные случаи разбора аргументов (несущественное)

[`option_value`](../../../ynwa-player/src/cli.rs:88) отвергает любое значение, начинающееся с `--`,
поэтому файл/каталог с именем `--…` задать нельзя; одиночный флаг вида `-x` трактуется как
позиционный аргумент, а не как неизвестный флаг. Для реального использования маловероятно, но
формально «неизвестный флаг → ошибка» выполняется только для `--…`.
