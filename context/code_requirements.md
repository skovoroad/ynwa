# Требования к коду

1. Код должен быть по возможности простым. Если есть возможность избежать шаблона, трейта в пользу простых структур и функций, это следует сделать.
2. не нужны очевидные комментарии: комментарии только к неочевидным местам. В комментариях к функциям нельзя писать, откуда они вызываются. Нужно комментировать только неочевидные вещи, которые невозможно понять из кода, и API.
3. Использовать говорящие идентификаторы
4. проекту свойственна высокая комбинаторика, поэтому следует добиваться максимального покрытия тестами, по возможности параметризованными.  Юнит-тесты в отдельных файлах `*_tests.rs` рядом с реализацией, подключаются через
`#[cfg(test)] #[path = "..."] mod tests;` — это уменьшает размер файлов реализации и контекст для агентов. Тривиальные присваивания не тестируются; проверяются логика, границы, интеграция.
В новом коде тестами покрываются все пути. При необходимости, если это уместно (входные условия принципиально влияют на результат), тесты должны быть параметрическими.
5. разумеется, все тесты должны быть зелёными.
6. cargo clippy и cargo fmt не выдают предупреждений.
7. Типобезопасность (например, `uom` вместо `f32`), валидация в конструкторах через `assert!`,
8. описание данными вместо алгоритмов, идиоматичный Rust (`Option`/`Result`), O(1) на горячих путях,
9. YAGNI — реализуется только явно запрошенное в задаче или задании. Это важно! Ничего не выдумывать за пределами спецификации, не добавлять не запрошенные изменения. Если они нужны - сначала обсудить с человеком.
10. При написании тестов надо стараться переиспользовать существующую инфраструктуру: хелперы, билдеры и проч. При необходимости выносить их в файл с тестовыми утилитами.
11. Методы типа (`impl`) размещаются в том же файле, где объявлен сам тип; не добавлять inherent-`impl` для типа из другого модуля/файла. Это не относится к реализациям трейтов — для них допустимы отдельные модули-компаньоны.
